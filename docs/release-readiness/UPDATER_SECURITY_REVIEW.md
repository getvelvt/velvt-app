# Velvt Updater Security Review

Review date: 2026-07-22
Reviewer role: independent updater security and release-gate review
Production code modified by reviewer: none

## Verdict

**Implementation verdict: PASS for source/local structural readiness. Production
activation verdict: P0 / release gate closed until a real, credentialed
N-to-N+1 exercise passes.** The selected whole-bundle Sparkle design is
appropriate for keeping the Swift app and embedded Rust service on one IPC
protocol version. A source-level integration, local build, or the presence of a
Sparkle dependency is not evidence that updates work securely.

Lead-resolution addendum: the later integrated pass closed the reviewer’s
locally actionable production-API and architecture-policy findings. Release now
requires an explicit production URL plus a separately approved exact hostname,
and the final local app/helper are universal `arm64 x86_64`. The real Sparkle
2.9.4 adversarial harness cryptographically verifies valid archive/feed
signatures and rejects wrong-key, modified, and truncated inputs. These local
closures do not change the production P0 verdict.

The implementation must use an exact Sparkle **2.9.4** pin, not the previously
proposed 2.9.2. Sparkle's current security notes identify 2.9.4 fixes for delta
symlink handling and an appcast-item spoofing race. The production plist must
also set `SUSignedFeedFailureExpirationInterval` to `0`; Sparkle otherwise lets
signed-feed failures expire after 20 days.

## Threat model

| Threat | Required control | Release evidence |
|---|---|---|
| Feed or release-notes tampering | HTTPS, `SURequireSignedFeed=true`, `SUVerifyUpdateBeforeExtraction=true`, signed feed generated by Sparkle, failure expiration `0` | Modified-feed and modified-release-notes tests fail closed indefinitely |
| Archive tampering or truncation | Sparkle Ed25519 archive signature, exact byte length, verification before extraction | Byte-flipped and truncated archive tests leave N installed and permit later retry |
| Malicious replacement signed by another party | Developer ID identity continuity plus Ed25519 verification | Wrong Team ID and wrong Ed25519 key tests fail without replacement |
| Downgrade or same-version replay | Candidate `CFBundleVersion` must compare numerically greater than installed; immutable archive URLs | Release gate rejects lower/equal/malformed versions; staged downgrade feed is ignored |
| Swift/helper version skew | Update the entire app bundle atomically; verify embedded helper protocol before publication and after relaunch | N+1 app/helper versions and IPC protocol agree |
| Partial install or power/network failure | Sparkle atomic replacement, full-archive fallback, retry path | Offline, interrupted, read-only destination, and broken-delta tests preserve N |
| Migration damage | Additive/forward-safe SQLite migrations; immutable pre-update fixture; never treat app rollback as a DB rollback | Counts/checksums and schema checks before/after; forward-repair owner identified |
| Credential or key disclosure | Ed25519 private key only in Keychain/offline release store; Developer ID/notary credentials only in protected CI/Keychain | Repository and build-log scan; documented custody, backup, rotation, revocation |
| Privacy leakage in update checks | No custom feed parameters/headers; `SUEnableSystemProfiling=false`; no activity, insight, auth, DB, or device-profile fields | Captured request contains only normal HTTP/Sparkle request metadata |
| Host compromise/publish race | Upload notarized immutable archive first, verify reachability/hash, atomically publish signed appcast last; retain N | Publishing transcript and rollback/forward-repair runbook |
| Dependency compromise | Exact 2.9.4 pin and committed resolution; review updates intentionally | Resolution file and packaged framework version match the approved version |
| Nested-code signing failure | Sign Sparkle's framework/helpers/XPC services inside-out and outer app last, using the same release identity where applicable | `codesign --verify --deep --strict`; nested signature/team inventory; notarization acceptance |

## Mandatory production gate criteria

All gates are conjunctive:

1. Exact Sparkle 2.9.4 dependency and committed `Package.resolved`; both the
   Xcode app target and Swift package tests resolve the intended version.
2. `SPUStandardUpdaterController` is retained for the app lifetime. The manual
   **Check for Updates…** action invokes Sparkle and is disabled safely when
   production update configuration is absent.
3. Final production `Info.plist` has an HTTPS `SUFeedURL`, a 32-byte Ed25519
   `SUPublicEDKey`, `SURequireSignedFeed=true`,
   `SUVerifyUpdateBeforeExtraction=true`,
   `SUSignedFeedFailureExpirationInterval=0`, and
   `SUEnableSystemProfiling=false`. Debug/local builds cannot silently contact
   the production feed.
4. The first appcast candidate is strictly newer than the installed numeric
   `CFBundleVersion`; it has an HTTPS enclosure, positive exact length, valid
   Ed25519 signature, supported minimum macOS, and the intended channel.
5. The signed feed and archive are generated/verified with Sparkle's tools.
   XML shape or base64 length checks alone are insufficient cryptographic proof.
6. `Velvt.app`, the embedded Rust helper, Sparkle framework, and all Sparkle
   nested code pass strict code-sign verification. Production components have
   the expected Team ID and hardened runtime, and the final DMG is notarized and
   stapled.
7. The exact notarized N and N+1 artifacts pass the matrix below from
   `/Applications`; update checks from a development build do not satisfy this
   gate.
8. Authentication, Keychain items, preferences, Accessibility and Notification
   authorization, database schema, row counts, and privacy boundary survive the
   update. No raw activity content is recorded in evidence.
9. Archive-first/appcast-last publishing, retention of the prior full archive,
   key custody/rotation, and forward repair are assigned to named owners.

## Required N-to-N+1 matrix

Use two Developer-ID-signed and notarized builds with distinct increasing build
numbers and a controlled HTTPS feed. Run each negative case from a fresh copy of
N, then verify a valid retry succeeds.

| Case | Expected result | State assertions |
|---|---|---|
| Valid full archive N→N+1 | Prompt/download/install/relaunch succeeds | N+1 app and helper run; protocol matches; auth, DB, preferences, TCC status preserved |
| Automatic check consent | No unconsented profile submission | Request has no profile or Velvt activity data; user choice persists |
| Appcast modified after signing | Reject | N remains intact; clear safe error; retry works |
| Release notes modified after signing | Reject or omit untrusted content | No attacker-controlled content rendered |
| Archive byte modified after signing | Reject before extraction | N remains intact; no partial bundle |
| Truncated archive / wrong length | Reject | N remains intact; cache can recover |
| Wrong Ed25519 key/signature | Reject | N remains intact |
| Wrong Developer ID identity/Team ID | Reject | N remains intact |
| Same or lower build number | No install | No downgrade/replay |
| Unsupported minimum macOS | No offer/install | Existing app remains usable |
| Offline/timeout/TLS failure | Recoverable error | App remains usable; bounded retry |
| Read-only/unavailable destination | Recoverable error/authorization UX | No partial replacement |
| Interrupted install/relaunch | Atomic recovery | Either complete N or N+1 exists, never mixed app/helper |
| Broken delta with valid full archive | Full archive fallback succeeds | N+1 state assertions pass |
| N+1 startup/helper/IPC failure | Recovery procedure works | Reinstall last-known-good full DMG without deleting data, or publish forward repair |
| Version-N database migration | N+1 reads/migrates fixture | Schema and non-content counts/checksums match expectations |
| Feed key rotation | Only documented valid rotation succeeds | Old and new trust roots handled per policy; no simultaneous Developer ID and Ed25519 rotation |
| Update server compromise simulation | Unsigned/misdirected feed rejected | No alternate archive host or untrusted release notes accepted |

## Findings

### P0

- **Open activation blocker:** no production N-to-N+1 or adversarial-path
  evidence exists yet.
- **Resolved in implementation:** stale Sparkle 2.9.2 was replaced with exact
  2.9.4, including committed resolution evidence.
- **Resolved in implementation:** the manual signer and verifier now enumerate
  Sparkle nested code inside-out, preserve Downloader entitlements as required
  by Sparkle 2.9.4, reissue designated requirements under Velvt's identity, and
  verify nested signatures, Team ID, and hardened runtime in production mode.
- **Resolved in implementation:** production release now requires and explicitly
  passes updater enablement, feed URL, public key, N and N+1 build numbers,
  version, Sparkle tool path, external private-key file, and immutable outputs.

### P1

- The static readiness gate verifies signed-feed/enclosure shape, decoded
  sizes, signed-content byte length, checksummed archive bytes, and version/URL
  binding. The separate local adversarial harness uses Sparkle 2.9.4's real
  tools for cryptographic acceptance/rejection. Actual packaged replacement and
  relaunch remain an E2E gate.
- Production host ownership, key custody/rotation, archive retention, immutable
  URLs, and publish ordering have no executed evidence.
- Rollback is unsafe after irreversible migrations; forward repair and fixture
  migration tests must exist before activation.
- ZIP updates limit emergency Ed25519 key-loss recovery compared with a
  Developer-ID-signed DMG under verify-before-extraction. Planned rotation while
  the old key remains available is still possible; document and test the chosen
  recovery path.

### P2

- The release generator accepts a caller-supplied Sparkle tool directory but now
  requires approved SHA-256 values for both Sparkle tools. Production must still
  record those values and the verified tool bytes in its evidence ledger.
- Update UX on read-only/translocated/managed installations needs validation.

### P3

- Preserve privacy-safe updater diagnostics (status/error code, version, and
  host only); never log feed contents, release-note contents, raw activity, or
  tokens.

## Open blockers

- Real HTTPS update host and immutable publishing mechanism.
- Ed25519 private-key provisioning, backup, rotation, and incident owner.
- Developer ID and notarization credentials.
- Two notarized increasing-version artifacts and a clean test installation.
- A completed matrix with privacy-safe evidence.

Confidence: **high** for the threat model, implementation review, and current
activation blockers; **no claim** is made that production updates work until the
credentialed packaged N-to-N+1 matrix is complete.
